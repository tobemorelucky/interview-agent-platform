## 1. 写作与使用原则

### 1.1 面试表达顺序

先说产品问题，再说设计理由，然后说关键机制和效果，最后主动承认一个取舍：

```text
问题 → 为什么这样拆 → 怎么工作 → 关键机制 → 解决什么 → Trade-off → 下一步
```

“解决什么”优先描述可以从实现证明的性质，例如旧上下文不漂移、失败不伪造评分、未审批不写长期记忆；没有实测就不说效率提升百分比。

### 1.2 不从代码名字开始

不要开场介绍某个 endpoint 调到某个 service。先讲“面试过程需要稳定状态，而模型只能给建议”，被追问后再解释版本校验、短事务和唯一约束。技术栈用于解释选型，不作为项目故事的主体。

### 1.3 一人称模板的边界

文中“我”的段落是口述练习模板。使用前应按自己的实际参与改成“我设计”“我实现”“我验证”或“项目采用”，不要把工具或他人的工作全部包装成本人独立完成，也不虚构用户调研、线上故障或业务收益。

### 1.4 三种陈述必须分开

- 已实现：当前源码支持的机制。
- 已验证：验收实际覆盖的环境与输入。
- 如果继续做：明确的未来方向，不混进现有成果。

“独立评价”指职责、Prompt 和调用分离，不代表不同模型、统计独立或评分准确率已验证。“Evidence”代表可追溯支持，不是内容绝对真实的证明。

## 2. 项目定位与四种时长介绍

时长是练习目标，取决于语速。先掌握意思再口述，不必逐字背诵。

### 2.1 一句话（约 50 字）

这是面向秋招的多 Agent 求职与模拟面试平台，以证据化画像连接岗位匹配、独立评价、面试复盘和受控成长记忆。

### 2.2 30 秒介绍

我做的是面向秋招的多 Agent 求职与模拟面试平台。它先把简历变成带证据的候选人画像，再支持选择或推荐岗位，进行多轮面试、独立回答评价和复盘。核心不是让模型包办，而是用程序控制状态、证据和统计，长期记忆也要用户批准。验证采用稳定 Replay 和真实 DeepSeek 两条路径。

### 2.3 1 分钟介绍

这个项目想解决求职准备割裂的问题：简历、岗位要求和练习记录通常没有连接，普通聊天式面试也缺少稳定过程。我先把简历整理成有依据、可修正的 Candidate Profile，让匹配和面试使用同一份候选人材料。岗位匹配先做结构化召回、资格检查和证据对齐，再让模型排序。面试中出题和评价分成两个角色，程序控制追问、深挖和结束。复盘数字从真实评价记录计算，Coach 只做分析；长期记忆只产生建议，用户确认后才能写入。六个正式角色完成了真实 DeepSeek 验收，同时用 Replay 检查状态、引用和重试边界，未把本地数据当成 Live Search。

### 2.4 3 分钟完整介绍

我的项目是面向秋招的多 Agent 求职与模拟面试平台。我关注的不是再做一个能问答的聊天窗口，而是把简历、岗位要求、练习过程和复盘连接成一条有依据、能恢复的准备流程。

首先是候选人材料。每次把整份简历直接交给模型，容易得到不同解读，后面也难追溯。我保留原上传解析链路，在它上面生成统一 Candidate Profile。技能、项目和经历都关联原材料依据，用户修正产生新版本。材料没写某技术，系统只能说当前未提供证据，不能断言用户不会。

其次是岗位匹配。不是让模型面对全部岗位打分，而是先用结构化规则召回有限候选，检查资格，再形成岗位要求和候选人证据的对齐矩阵。模型在允许集合内做相对排序，程序决定最终政策。明确不满足的岗位不参与正常推荐，未知资格不能猜成满足，界面不展示没有校准依据的匹配百分比。

最核心的是面试。出题角色负责题目和追问内容，评价角色只评价本轮回答，程序 Controller 决定是否追问、深挖、下一题或结束。开场固定画像、JD、公共题库实际内容与已批准记忆，避免过程漂移。模型调用不长时间持有业务锁，回来后重新校验状态版本；回答有幂等身份，数据库提交后才发结果事件。评价失败不会默认给分或直接推进。

结束后，五维均值等数字从有效评价记录计算。Coach 只能引用本场评价形成优势、问题和练习建议，不能重新评分。表现观察与稳定候选事实分开，想进入长期记忆的内容先成为 Proposal，由用户批准或修正，下一场才会读取。

公共 Research 是后台数据补充链路，不在用户每次操作时爬网页。搜索发现 URL，抓取正文才建立正式证据，采集和抽取都有审计。当前 Live Search 受上游限制，稳定演示使用明确标记的 Fixture/Replay。

验证上，我用同一业务流程下的 Replay 做边界和故障回归，又让六个正式角色用真实 DeepSeek 跑通核心链路。真实模型暴露过技能证据状态过高的问题，最后不是删除校验，而是把最高支持状态交还程序计算。项目还没有大规模生产验证，我认为最有价值的成果是建立了模型生成、确定性业务规则和用户授权之间清晰的边界。

## 3. 从产品问题解释为什么做

| 求职准备的问题 | 项目怎么处理 | 不夸大的效果 |
| --- | --- | --- |
| 简历只作为附件，信息没有复用 | 统一、证据化的 Candidate Profile | 后续流程使用同一份候选事实，不各自重新解析 |
| 练习题与本人和岗位脱节 | 固定候选材料、JD、要求和批准题库 | 问题有来源和场景，不承诺一定预测真实面试 |
| 普通聊天不知道当前进行到哪里 | 程序管理状态、题目身份和预算 | 可判断当前题、允许动作和失败后恢复位置 |
| 同一角色出题又评分，职责混杂 | 分开 Main 和 Evaluation | 容易检查各自输出，不能据此证明评分无偏 |
| 多次练习之间只堆聊天记录 | Observation、Proposal 和批准 Memory 分层 | 下一场可参考确认内容，不自动给用户贴能力标签 |
| 模型提出无依据的判断 | Evidence ID、支持校验、保守状态收敛 | 对引用与若干字段加约束，不宣称消灭所有幻觉 |

产品上的中心是“练习—评价—复盘”，Research 是供给侧，Agent 数量是职责拆分的结果，不是产品目标。

## 4. 向面试官讲整体架构

### 4.1 一条用户主链

```text
简历 → Candidate Profile → 推荐 / 指定岗位
    → 固定本场上下文 → 多轮面试 → 独立回答评价
    → 全场复盘 → 用户确认的长期记忆 → 下一场
```

可用三层表达：

1. 材料层：公共岗位数据与用户简历事实分开，保留来源。
2. 决策层：模型生成内容，程序控制资格、状态、证据和发布。
3. 成长层：复盘本场表现，用户决定哪些内容长期保留。

这样拆的原因是信息的语义不同：简历事实不等于某次回答表现，岗位要求不等于用户能力，模型建议不等于用户确认。各层不能用一个大聊天历史混起来。

### 4.2 公共 Research 单独介绍

它负责补充 Company/Job/JD/面经/题目，先发现 URL，再抓正文，再抽取带来源的数据，经过质量规则或审核。普通用户只能用已发布可用数据；不足时提示覆盖不足，不在线触发采集。

取舍是演示与在线产品不依赖不稳定搜索，但真实公共库覆盖、审核和发布衔接仍是后续工作，不能说已完成自动持续更新的招聘数据平台。

### 4.3 技术选型被问到时

主业务是有关系、有状态、有事务的流程，所以用 PostgreSQL 保存正式事实和过程。上传文件放对象存储，解析放 Worker，前端用 SSE 接收长请求结果。Milvus 保留既有知识/已发布内容检索能力，但新面试主要读取固定上下文。选择模块化单体是为了让领域边界明确，又不提前承担分布式服务协调成本。

## 5. 六个 Agent 怎么介绍

| 角色 | 为什么单独拆 | 输入 → 输出 | 不能做什么 / 如何协作 |
| --- | --- | --- | --- |
| Public Data Research | 来源处理与个人准备不同，需公共审核 | 已抓正文依据 → 岗位/JD/要求或面经抽取 | 不能编来源、写用户事实；向公共库供给，非用户实时搜索 |
| Resume/Profile | 建立后续共用的候选事实边界 | 简历报告和原文证据 → 候选事实与未知信息 | 不能认证精通、覆盖确认；由程序校验与发布版本 |
| Job Matching | 受资格和证据限制的候选比较 | 有限岗位、资格、矩阵、批准偏好 → rerank/关联 | 不能翻转资格或编技能；程序合成最终排序 |
| Interview Main | 专注如何问，不同时当裁判 | 固定上下文、历史、合法动作 → 题目与要点 | 不能推进会话或打分；Controller 校验发布 |
| Answer Evaluation | 专注本轮回答表现 | 问题、rubric、回答 → 五维评价与下一动作建议 | 不能插题、结束或改长期能力；Controller决定动作 |
| Summary/Coach | 局部评分与全场复盘语义不同 | 本场材料、有效评价、统计 → 分析/计划/记忆建议 | 不能重算评分或自动记忆；Report服务发布，用户审批 |

### 为什么不用一个超级 Agent

不是说单 Agent 不能生成这些文本，而是它把事实抽取、评分、流程控制和长期写入混在一个权限域里，出错后难判断失败在哪一步。拆分让每个角色的输入、输出和禁止动作可检查，也能单独重试。

Trade-off 是调用更多、延迟和编排成本上升。六角色不是六个独立部署的服务，也不是六种不同基础模型；这是业务职责拆分，不应描述成自主协商的分布式 Agent 群。

## 6. 最核心思想：LLM 与程序分工

LLM 处理抽取、语言生成、本轮评价和定性综合。程序负责已知规则与可计算事实：状态、证据身份、资格、计数、排序政策、事务、幂等和版本。

### 6.1 五个真实例子

| 例子 | 模型可以做 | 最终真相由谁决定 |
| --- | --- | --- |
| source_count | 不能决定最终来源数量 | 规范化正文 fingerprint 分组；同文转载不增加独立内容数 |
| Profile skill state | 提出 MENTIONED/DEMONSTRATED/STRONG_EVIDENCE | 引用的实际使用证据决定最高支持状态，只向下收敛 |
| Interview COMPLETE | 提出动作建议 | Controller 检查状态、题目、时间、轮次和预算 |
| Report averages | 读取并使用统计背景 | 数据库有效 Evaluation 重算；Coach输出没有平均分字段 |
| Job eligibility | 在允许候选中排序 | 结构化检查；NOT_SATISFIED排除，UNKNOWN保留 |

来源数量的精确含义是“独立规范化文本数量”，不是已证明独立作者数量；最高技能状态是证据等级，不是能力等级。

### 6.2 可以直接说的回答

“我没有把所有逻辑交给 Agent，因为文本理解和业务授权是两件事。模型可以评价一个回答、提出追问，但不能决定数据库当前题是谁；它可以提出技能状态，但不能替不存在的证据背书。我把可计算的数字和资格交给程序，把模型输出当成待校验的 artifact。这样失败时可以停在明确节点，历史和长期事实不会随着一次不稳定生成被改掉。代价是规则比较保守，编排也更复杂。”

继续做时，应优化规则覆盖与语义支持验证，而不是取消边界换取更流畅的表面结果。

## 7. Candidate Profile 设计

### 7.1 为什么不每次直接扔原始简历

重复读取大文本成本高，不同模块可能给出不同解释，用户也不知道如何纠正。统一画像让技能、项目、教育和工作事实成为可复用材料，原简历仍保留作依据。

当前不是自由生成“精美个人评价”，而是偏保守的证据化抽取。后续 Matching 读取规范化事实，新面试读取固定版本，不各自重新解读全部 Resume。

### 7.2 证据、版本和用户修正

Evidence 由程序切分原文、记录位置和稳定身份。模型只引用它，不能重新生成 excerpt。画像按完整版本发布，失败不切 current，用户纠正继承旧内容生成 N+1，并区分用户确认与原文依据。

版本化解决“纠正后历史面试为什么变化”的问题，Trade-off 是重复保存和较严格的修正流程。用户确认仍是自述，不是外部核验。

### 7.3 Redis 真实案例

真实验收时模型提出 Redis 是 STRONG_EVIDENCE。程序只在被引用的项目/工作/实习证据中找到一条具体使用支持，因此最高是 DEMONSTRATED，最终降到这个状态。

规则是：没有具体使用支持最多 MENTIONED；一条最多 DEMONSTRATED；至少两条不同支持最多 STRONG_EVIDENCE。只计算实际引用、真实存在且含技能的证据，不自动补引用；没有合法支持仍拒绝。

这解决的是“把材料中的一次使用夸大成多处强支持”，不是证明 Redis 技术水平。状态不是百分制熟练度。

### 7.4 “没写”和“不会”

材料不覆盖某技术，系统只说当前未提供证据。是否掌握要通过新材料、用户确认或之后的实际回答观察，不能从简历遗漏得出能力否定。

进一步追问可查 28 号第 6/8 节；机制是稳定 Evidence、支持校验、完整版本与最后 current 切换，不必先背表名。

## 8. Job Matching 设计

### 8.1 两阶段，不是模型打分器

```text
bounded SQL / structured retrieval
    → Eligibility → Evidence Matrix → pre-rank
    → LLM rerank / 选择解释关联
    → deterministic final policy
```

先把状态、类型、地区、标签和明确排除等结构条件处理掉，限制送给模型的集合。资格回答“允许不允许、知道不知道”；Fit回答“当前材料支持哪些要求”。技术相关不能覆盖明确排除。

### 8.2 UNKNOWN 的价值

当前学历、专业、毕业年份没有可靠候选结构字段。碰到对应限制，保持 UNKNOWN，不从自由文本或 Memory 猜。UNKNOWN可以成为探索结果，但不能包装成已满足。

SATISFIED 是已有规则下的已满足，不是公司HR资格认证；示例中的明确不满足来自地区等可靠输入，不是系统已完成全面学历筛选。

### 8.3 Evidence Matrix

把岗位要求与候选事实/依据组成可检查的关联，分为 SUPPORTED、PARTIAL、NO_EVIDENCE、NOT_APPLICABLE。当前用字面规范化匹配，不用 embedding猜技能别名。模型只选择给定关联，解释必须复制程序支持文本，不能开放式生成新能力结论。

### 8.4 排序和等级

pre-rank记录程序预排，agent-rank记录模型相对顺序，final-rank按固定资格/证据层级合成。模型在同层中有选择空间，不能越过政策。推荐等级受证据上限约束，用高度匹配/较为匹配/可尝试/信息不足，不显示未经标定的87.43%。

Trade-off：可解释和保守，但literal规则可能漏同义表达，资格未知也多；未来可增加受验证的归一化和结构化资格，不用模型直接填未知。

### 8.5 1 分钟标准表达

“我把岗位匹配拆成程序筛选和模型比较两阶段。先用结构字段召回有限岗位，确定资格，再把岗位要求和候选证据做成矩阵。明确不满足的岗位不交给模型，缺可靠学历信息就保留未知。模型只能在这个集合里排序和选择已有证据关联，最终顺序还要按版本化政策合成。我保留预排、模型排和最终排，便于解释排序变化。界面展示推荐等级而不是百分比，因为当前没有真实录取数据校准。这种设计的代价是保守、语义覆盖有限，但不会让语言流畅度掩盖证据或资格不足。”

## 9. Multi-Agent Interview：核心设计

### 9.1 普通 Chat 的问题

聊天历史不天然定义当前题、有效回答、已完成评价和合法下一步。重试会重复文本，追问可能无止境，模型出题与评分混杂，网络失败也可能造成前端和数据库对不上。

我把面试当作有状态业务过程，而不是靠聊天历史猜进度。

```text
Main产生题目 → 用户回答 → Evaluation评价
    → Controller校验 → FOLLOW_UP / DEEP_DIVE / NEXT / COMPLETE
```

Controller 也控制首题、跳过、问题发布，不只是评价后的最后一步。

### 9.2 设计问题 → 解决方式

| 设计问题 | 处理方式 | 取舍 |
| --- | --- | --- |
| 同角色自出题自评，权限混合 | 出题/评价分开Prompt与调用，共享固定材料和rubric | 便于审计，不保证两者统计独立或无偏；可能共享rubric偏差 |
| 模型擅自跳题/结束 | 模型只返回artifact，Controller唯一写状态 | 编排复杂，规则优先于模型建议 |
| 动态题导致数组index漂移 | 用active question身份、状态和顺序确定当前题 | 需维护关联和派生兼容index |
| 无限追问 | 根题次数、总题量、轮次、时间与reservation预算 | 可能提前结束，不能宣称精确token计量 |
| 失败仍显示评价 | 不生成默认分、不自动NEXT，保存失败可重试 | 用户需要等待/重试 |
| 慢模型阻塞数据库 | 读状态后关事务，模型返回后短锁重验 | 过期模型结果可能浪费成本 |
| 双请求覆盖 | expected state_version与active/Answer检查 | 冲突返回刷新，不强行合并 |
| UI显示结果但DB未提交 | 结果事件在commit后发 | 长请求期间先只有status提示 |
| SSE跨网络chunk | 持续parser/decoder，完整事件边界再解析 | 需专门处理残片和UTF-8 |

### 9.3 FOLLOW_UP 与 DEEP_DIVE

FOLLOW_UP围绕当前回答缺失点补问；DEEP_DIVE围绕技术/项目主题继续深入。当前二者都持久化为带父题的新SessionQuestion，分别有回答和评价，差异在语义、kind/source与动态统计，不是“追问完全没有独立记录”。

### 9.4 失败与结束

Evaluation失败保留失败审计和回答，不成功EVALUATED，不NEXT，更不能补一个3分。Controller可以因确定性预算耗尽结束而没有本轮评价，但要明确未评分，不能伪造成模型评价成功。

一轮评价成功而下一题生成失败时，正式评价也可能还未发布；同回答重试可能再次调用模型。这是完整发布边界的代价，不是exactly-once推理。

### 9.5 并发例子

两个请求读到同一版本。模型返回快的请求提交推进，另一个回来发现状态版本或当前题不一致，拒绝覆盖。短事务有行锁做最终检查，不能只在调用前检查一次。这个机制保护业务一致性，不等于做过高并发压测。

深入入口：28号第5/8节。常规面试先讲状态/权限，只有被问时再说active_question_id、state_version与唯一约束。

## 10. Evidence Grounding：不只是 RAG citation

传统citation通常展示检索文本出处，本项目还把依据作为写入约束和身份边界：模型不能仅给一个看起来像引用的字符串。

候选侧：`Resume → 确定性ResumeEvidence → Candidate facts/Profile`。

公共侧：`Source → Fetch Snapshot → 确定性正文span → ClaimEvidence支持Claim → Job/JD Requirement`。

两侧进入Matching矩阵；面试固定相关事实、依据与公共问题；报告再引用真实Evaluation，不把评价当简历事实。

### 为什么只给ID、程序回填

excerpt若由模型重写，即使URL真实也可能是假引文。程序先建立catalog，模型选已有ID，程序核对存在性和本次范围，再取原文和位置。Profile还检查事实是支持excerpt中的连续内容。

这能拒绝未知ID、错场评价、未提供来源和一些无支持判断，但ID合法不代表陈述必然语义正确。公共要求没有与Profile完全同等的逐字校验，不能说所有Claim已形式化证明。

### 两个防混淆例子

- JD要求Kafka只证明岗位要求，不证明候选人会Kafka。
- 评价说本轮coverage低只证明模型对这次回答的观察，不证明长期能力差。

NO_EVIDENCE表示当前材料未覆盖，不是能力否定。Trade-off是漏召回和表达保守；继续做应增强支持规则与诊断，而非让模型补造证据。

## 11. Version Pinning：本场不能换底稿

场景：面试已经开始，用户更新简历、管理员改JD或题库、用户批准新Memory。当前面试不应该中途变换背景，否则前后难度、评价标准与历史解释都不稳定。

设计是材料版本 + 本场Snapshot：Profile有版本，JD有版本；创建会话时固定所用版本及实际要求、题库内容、fingerprint、依据和Memory。公共题库/面经不是不可变版本，所以不只存ID，也保存本次必要内容。

后来更新影响下一场，不替换本场。Memory与近期Observation分别固定并有独立预算，运行每轮不重新读取最新内容。

MatchRun与InterviewSnapshot不同：前者解释当时为什么推荐，后者固定本场使用的材料。从历史推荐启动只传公司/岗位，重新校验可用性、当前默认材料与批准Memory。岗位关闭就拒绝，不改历史推荐。

Trade-off是冗余和存储成本，还要区分“历史可解释”和“重新运行完全相同结果”：固定输入不能保证在线模型输出逐字相同。

## 12. Controlled Memory：不是自动保存所有回答

```text
Evaluation → PerformanceObservation → PENDING MemoryProposal
    → 用户approve / correct / reject → Long-term Memory
```

Kafka例子：可以观察“本场Kafka一致性问题回答深度不足”；不能直接写“用户Kafka很差”。面试表现受题目、表述和本次状态影响，候选稳定事实则来自简历或用户确认。

Proposal有Session/Report与支持评价，用户可看依据、修正或忽略。approve/correct将Memory、事件和决定一次事务提交；reject不写Memory。保留原内容和修正内容，不覆盖原提议。

第二场读取两组背景：用户确认的Memory与近期表现观察。前者也不是客观认证，后者更不能当稳定个人事实。两组数量/预算独立，固定入Snapshot，本场不动态更新。

取舍是确认步骤增加操作，但避免一次输出污染长期画像。当前面试不自动更新Profile/UserSkill；旧显式Memory接口保留，不能让新流程通过旧consolidate绕审批。

### 面试直接回答

“我的Memory不是聊天记录压缩后自动保存。模型先提出本场有依据的观察，再产生待批准建议，用户决定是否长期保留。一次表现不足不能成为稳定技能标签，下一场也会区分批准记忆和临时观察。这样降低错误长期积累的风险，代价是需要人工确认和更复杂的provenance。”

## 13. Replay：复现的是业务流程

Replay用固定外部结果替换Provider，仍使用同一Contract、Schema、validator、Controller、事务和正式持久化路径。网络Replay不接真实外网，也没有fixture缺失时联网补救。

因此回归关注“这组输出能否合法推进、是否重复写、失败是否rollback”，而不是等待搜索或模型这次是否给同样结果。比另写mock业务路径可靠，因为不会绕开关键领域规则。

Trade-off是固定输入不能证明线上模型会持续产生合格结果、网络可达或评分真实。所以还需要Real Model：六角色实际DeepSeek验证兼容性、输出和resolver。Replay与Live互补，不互相冒充。

演示明确标记DEMO/Replay，真实模型验收标记LIVE model + Fixture data。不是“整个系统全部联网真实数据”。更大的场景覆盖和Provider变更回归可继续增加，但没有当前生产效果指标。

## 14. Reliability：怎么把工程细节讲成设计

| 遇到的问题 | 设计 / 为什么 | Trade-off与下一步 |
| --- | --- | --- |
| 输出语言流畅却无法消费 | 结构输出+应用Schema，先检查契约 | 合法结构不保证正确语义；不是所有Provider原生strict schema |
| JSON/结构错误 | 最多一次constrained repair，保护事实字符串和引用 | 仍可hard fail，不是无限修复或全语义证明 |
| 真实ID却没支持 | deterministic resolver与字段规则 | 保守、有漏判，需完善支持诊断 |
| 请求重发重复记录 | 稳定业务key、unique、结果复用 | 防重复发布，不保证只调用模型一次 |
| 模型期间会话变了 | expected version + 短锁重验 | 过期推理浪费token；不是自动合并 |
| 慢模型长锁 | 核心面试先关读事务再调用 | 不是全仓库统一无长事务，Research仍有边界 |
| 同场材料变化 | 版本固定和最小实际内容Snapshot | 存储冗余，不能承诺真实模型完全复现 |
| 重试覆盖新结果 | attempt fencing、失败历史与显式retry | Celery不等于完整自动backoff调度 |
| 不能定位失败 | 角色/provider/model/prompt/usage/error审计 | 不保存隐藏推理，usage没返回不猜成本 |
| 回归依赖网络 | Replay共用领域路径 | 必须另做真实Provider验证 |
| 新报告失败破坏旧报告 | 完整生成后原子切current | 多generation管理成本；Session完成不回滚 |
| Memory半成功 | Memory/事件/Proposal决定统一事务 | 外部存储/队列并未因此获得分布式事务 |

整体原则：让失败成为明确状态，不伪造成功、不丢历史。Provider fallback只针对明确不可用错误；Schema/Evidence/业务失败不能换模型刷成功，普通慢响应也不自动fallback。

当前并发guard是进程/事件循环内，不是全局分布式限流；上传MinIO/数据库/任务队列之间没有outbox总事务。这些是未来工程升级点，不能被“可靠性设计”掩盖。

## 15. 真实模型问题：STAR 回答

### 15.1 S：真实测试暴露了什么

“真实模型验收时，画像输出已经是合法JSON，也通过了结构Schema，但技能证据状态没有满足业务支持规则，链路停在Profile。说明格式正确和业务正确是两层问题。”

历史第一轮失败保留，没有删掉后改成成功。第一轮模型与第二轮最终模型不同，按要求恢复DeepSeek Primary是一项独立配置调整，不能把模型切换说成Evidence问题的解决方法。

### 15.2 T：要解决什么，不允许牺牲什么

“目标是在不删除Evidence validator、不伪造引用、不放宽strength规则的前提下，让最高证据状态不再完全依赖模型自觉。我需要保留事实抽取能力，同时把可计算的字段收回程序。”

### 15.3 A：怎么做

“模型可以提出状态，程序只检查被引用的真实证据：有没有具体项目/工作使用，一条还是至少两条。计算最高支持状态后取两者较低值，不向上提升。引用不合法仍失败，strength校验也保持。补充技能、原提议、最大支持、引用与规则的诊断，并重新跑回归和真实模型验收。”

### 15.4 R：结果与边界

“第二轮真实DeepSeek提出Redis为STRONG_EVIDENCE，程序收敛到DEMONSTRATED，符合实际引用的一条使用证据。六个正式角色最终都成功，核心Profile—匹配—面试—Coach链路落库，Replay回归仍通过。不是证明模型更准确，而是证明过高提议能被现有规则约束。”

F2当时回归201 backend / 7 frontend；最终工程冻结215 / 11。本次文档没有重新运行。真实F2所有成功结构首轮合格，repair=0；repair和hard-fail是测试覆盖，不是现场真实repair成功案例。Fallback备用模型也未真实调用。

### 15.5 1–2 分钟连续表达

“一个印象比较深的问题出现在真实模型验收。画像JSON没问题，但技能证据等级过高，业务validator把它拒绝了。我没有删掉validator，而是反思：这个等级本来就可以从引用证据计算，不应该全交给模型。于是让模型提议，程序判断最多支持到哪一级，最终只取较低值；无效证据仍然拒绝。DeepSeek第二轮把Redis提为强证据，程序按真实的一条使用证据降到已展示。最后六个角色和核心链路成功，旧失败记录也保留。我得到的经验是，不稳定生成未必靠更长Prompt解决，能确定性计算的字段应交还程序。”

另外保留了Matching超时和预算结束场次：延长明确等待后仍用同一DeepSeek重试，没有因慢响应fallback；新建smoke场次使用更高reservation上限，没有改旧Snapshot或Controller。不要说“第一次所有调用都成功”。

验收边界：本地JD/Snapshot、DEMO岗位和固定回答；TXT确实解析，但输入ResumeReport是fixture，不是完整上传/Celery/旧报告真实模型验收；最终FinalInterviewReport由LIVE Coach生成并真实持久化。28号末尾“F2 Report为fixture”的简写应理解为输入ResumeReport，不是最终面试报告。旧文档保持不动，在此澄清。

## 16. 八个最值得讲的设计亮点

### 16.1 Agent 与 deterministic boundary

- 问题：语言生成越过业务授权。
- 我的设计：模型提议，程序负责状态、资格、数字与发布。
- 为什么：把可计算规则变成可检查不变量。
- Trade-off：规则和编排复杂，较保守。
- 面试一句话：我限制Agent的写权限，而不是只要求它“不要出错”。

### 16.2 Evidence grounding 与向下收敛

- 问题：真实ID或技术提及被扩大成能力结论。
- 我的设计：已有Evidence引用、程序回填、技能最高支持状态。
- 为什么：控制无依据事实与证据等级夸大。
- Trade-off：literal校验可能漏合理概括，非语义真实性证明。
- 面试一句话：模型只能在已给材料内提事实，证据等级由程序限制。

### 16.3 Independent Evaluation

- 问题：出题、评分和长期判断混在一个角色。
- 我的设计：独立评价调用，只评本轮，输出五维与建议。
- 为什么：职责可审查，局部表现不污染长期事实。
- Trade-off：额外延迟；同基础模型与共享rubric仍可能同偏差。
- 面试一句话：独立的是角色和权限，不是声称有两个无偏裁判。

### 16.4 Controller、版本重验与提交后事件

- 问题：动态插题、重试与并发造成状态错乱。
- 我的设计：唯一状态写入口、active身份、短事务版本重验、commit后SSE。
- 为什么：浏览器和DB有明确结果边界。
- Trade-off：冲突可能浪费推理，完整轮次发布失败需重试。
- 面试一句话：模型决定内容，Controller决定这一步能否发生。

### 16.5 Version Pinning

- 问题：简历、JD、题库或记忆更新影响历史。
- 我的设计：版本化材料加本场实际内容Snapshot。
- 为什么：固定评价背景与来源。
- Trade-off：冗余存储；不保证真实模型逐字复现。
- 面试一句话：每场面试有固定底稿，新的材料只影响新的场次。

### 16.6 Controlled Memory

- 问题：一次失误变长期能力标签。
- 我的设计：表现观察、待批准建议、用户决定分层；审批单事务。
- 为什么：长期写入有证据与授权。
- Trade-off：用户多一步确认，provenance更复杂。
- 面试一句话：模型可以建议记住，但不能决定用户长期是谁。

### 16.7 Two-stage Job Matching

- 问题：全量岗位黑盒评分、硬资格被技术fit覆盖。
- 我的设计：召回/资格/矩阵先行，候选内rerank，固定final policy。
- 为什么：成本和权限有界，推荐原因可检查。
- Trade-off：资格未知多、字面匹配保守。
- 面试一句话：先决定可比较什么，再让模型比较，不让它猜资格。

### 16.8 Replay + Real Model Acceptance

- 问题：只测mock不知道真实兼容，只测Live无法稳定回归。
- 我的设计：同业务路径换Provider，分别验证规则与真实模型。
- 为什么：失败可重现，真实输出也受同样约束。
- Trade-off：fixture覆盖有限，smoke不是生产效果证明。
- 面试一句话：Replay证明过程可控，Real Model证明核心模型链路可运行。

## 18. 八个核心问题的三层回答

### 18.1 为什么 Multi-Agent

**Level 1 / 30秒：** 我按业务职责拆，不为追求Agent数量。事实抽取、岗位选择、出题、评价和复盘的权限不同，拆开后每一步可以检查和单独恢复，不让一个角色同时生成事实又授权写入。

**Level 2 / 1–2分钟：** 公共来源与个人事实分开，推荐只能比较合格集合，Main不能评分，Evaluator不能推进，Coach不能重新算分。每个角色看到相应输入、返回约定artifact，程序负责发布。代价是多次调用与编排复杂，但失败能定位是结构、依据、状态还是Provider问题。六角色并非六微服务，也并非六基础模型，减少偏差的效果还未做客观评测。

具体看一次回答，Evaluator负责五维和缺失点，程序据此允许补问，Main再生成针对性的题目。如果Main失败，不能由它自己猜下一状态，正式发布仍受Controller控制。这种分工也让失败恢复局部化：Coach失败不需要重跑已完成面试，Profile失败不影响原报告。拆分不是越细越好，否则只会增加成本；我按事实语义、权限和恢复边界决定角色，而不是把每个函数都包装成Agent。

**Level 3 / 源码：** logical routes、不同Prompt/Schema和resolver，Agent写调用审计而不直接修改面试业务；正式六角色之外仍有旧内部pipeline。下钻28第2/12节。

### 18.2 为什么 Controller

**Level 1：** 模型决定问什么、如何评价，程序决定当前是否允许追问、跳题或结束。过程状态不能靠聊天文本猜。

**Level 2：** Controller统一检查当前题、回答、预算、来源和版本，才发布评价与下一动作。FOLLOW_UP和DEEP_DIVE都占预算。模型失败不伪造分数、不NEXT；并发返回后重验，避免覆盖新状态。结果提交后才给前端。这个边界让动态面试仍是可检查的业务过程，代价是完整发布可能要重试、冲突推理浪费。

比如模型认为应该继续深挖，但本场剩余题量或时间不足，Controller不会照单全收；另一个请求已经推进时，也不能把旧题的结果覆盖当前题。我强调它是唯一状态入口，否则一部分旧service继续改index，就会有两套真相。当前题用稳定身份和状态表达，顺序只是展示辅助。这样模型生成与业务授权分开，回答完成、有效评价和会话结束都可以从数据库解释，而不是依赖最后一句聊天文本。

**Level 3：** active_question_id代替主真相index，state_version配短FOR UPDATE，prepare/commit_answer分阶段，保存result_events供同key重放。下钻28第5/8节。

### 18.3 Evidence 怎么做

**Level 1：** 候选与岗位各有原始依据。程序先建立可引用证据，模型只选ID，程序回填真实内容；缺材料不能解释为不会。

**Level 2：** Resume按确定性文本切分，公开内容必须真实Fetch正文而非snippet。Profile事实检查引用和连续支持，技能状态按具体使用证据限制。Matching固定两侧关联；面试固定来源；Coach引用本场有效评价。不同依据证明不同事情，合法ID也不等于语义绝对正确。当前规则保守，后续要增强支持验证，而不是让模型编excerpt。

比如岗位需要Redis，只能证明要求存在；简历某项目实际用Redis，才构成候选侧支持。如果模型提到的技能没有出现在引用中，即使引用ID真实也不能发布。真实测试里Redis状态被向下收敛，是把最高支持等级交给可计算规则，而不是证明候选人一定熟练。这种设计把“材料事实”和“能力判断”分开，代价是同义表达和合理概括可能被拒绝，所以我不会把Evidence grounding说成彻底消除幻觉。

**Level 3：** evidence_key包含材料身份/位置/hash，catalog解析exact span；matrix states；evaluation normalized refs。下钻28第6节。

### 18.4 Job Matching 怎么做

**Level 1：** 先程序召回和检查资格，做候选证据对齐，再让模型在允许集合内排序，最终顺序受固定政策约束。

**Level 2：** bounded集合避免全库送模型；明确不满足排除，未知保留。矩阵显示哪些要求有使用支持、只有提及、没有证据。模型选关联、不能自由加能力结论，pre/agent/final三rank解释分歧。等级有上限、不用概率百分比，批准偏好只作软输入。代价是literal覆盖有限和未知多，学历字段缺失不能硬猜。

用三岗位说明：一个有充分证据且现有条件满足，可以正常推荐；一个技术相关但学历资料不足，保留未知并作为探索；一个明确地区不符，则不参与rerank，不能靠技术优势翻转。最终排序先守资格与证据层，再使用模型顺序。历史Run还固定当时输入，后来更新画像不会改旧解释；用户点推荐开始面试时重新检查当前岗位，避免旧推荐绕过已经关闭的岗位。

**Level 3：** frozen MatchRun、REPEATABLE READ输入、policy版本、exact permutation、explanation exact-copy、lease与attempt fencing。下钻28第11/8节。

### 18.5 Memory 怎么做

**Level 1：** 面试表现先是观察，再是待批准建议，用户确认后才能进入长期Memory；一次失误不是长期标签。

**Level 2：** 每条建议有Session/Report和真实评价支持，用户可修正或拒绝。批准Memory与近期Observation分开预算、开场固定，本场不动态变化。审批把记忆、事件和决定统一提交，重复批准不写重复Item。Profile仍冻结，Memory自述也不是能力认证。代价是人工确认与更复杂的provenance。

例如用户接受“下一阶段重点练Kafka一致性解释”，这是确认的准备方向，不是系统认定他不会Kafka。另一个本场深度不足的Observation可供下一场参考，但必须标为表现观察。修正时保留原提议和新内容，拒绝时不写长期Memory。事务不能先调一个会commit的旧service再更新Proposal，否则中途失败就半成功。我更关注长期写入的授权和解释，而不是自动记住尽可能多的聊天。

**Level 3：** Proposal行锁/PENDING，repository只flush，API一个commit；original/corrected字段、UserMemoryEvent、两组Snapshot。下钻28第8/9节。

### 18.6 Replay 怎么做

**Level 1：** 只换外部Provider，不换业务逻辑，让相同输入可重复检查状态、依据和事务。再用真实模型验证外部兼容。

**Level 2：** 固定Search/Fetch/Model结果仍经过Contract、Gateway、resolver、Controller和DB。这样注入失败也能检查真实rollback，而不是mock掉状态路径。Replay禁外网，缺fixture明确失败。Real DeepSeek验证六角色的实际输出；数据仍标fixture，不宣传全Live。Trade-off是有限场景不能证明生产质量，需要持续扩覆盖。

我会把问题分开：确定输出下业务是否正确，与真实Provider是否能给出合格输出，不是一回事。Replay可以重复验证同Answer重试、审批并发和Snapshot不漂移；真实模型则暴露过技能状态过高与延迟超时。这些边界再加回稳定测试，才让一次真实发现成为长期回归。固定Provider不是伪装用户现场，DEMO/Replay标识也保留，验收结果不把搜索、模型和数据模式混写。

**Level 3：** ReplayModelProvider/ReplaySearch/Fetch实现同抽象，Task/Audit/persistence共用。下钻28第10/13节。

### 18.7 并发怎么处理

**Level 1：** 不持锁等模型。读取一个版本，回来短事务检查版本和当前题，陈旧结果拒绝；业务key防重复发布。

**Level 2：** 两请求同时读到同版本，不允许后返回的覆盖已推进会话。Prepare先保存可恢复回答，publish再绑定唯一有效评价。Report用attempt fencing防旧尝试替换current，Matching另有运行lease。注意这是业务一致性，不是已测大规模并发；模型可能重复调用，Provider guard也只是进程内。

最终检查需要在短事务里完成，不能调用前看一眼版本就认为安全。冲突后返回明确提示，不强行把两个不同过程合并。对同业务key已经成功的请求，可以读已有事件或结果，而不是再推进一次。这里我区分两种保证：数据库没有重复有效记录，不代表外部模型只调用一次。下一步如果成本成为问题，会增加调用协调与分布式限流，但当前不宣称具有全局exactly-once执行。

**Level 3：** expected version、FOR UPDATE、Answer/Evaluation unique、generation keys、partial current index、attempt_version。下钻28第8节。

### 18.8 失败怎么恢复

**Level 1：** 不伪造成功，保留已成功成果与失败审计，在同一业务身份上安全重试。旧current报告不受新失败影响。

**Level 2：** 格式问题最多一次repair，Evidence/业务失败明确停止，不换模型刷过。Profile失败不回滚Report；Evaluation失败不NEXT；Coach失败不回滚COMPLETED；新报告完整才换current；批准失败全rollback。明确Provider不可用可fallback，超时不自动换模型。Celery重投递有保护，但未做完整自动backoff调度；外部存储/队列也非总事务。

恢复必须继续使用稳定业务身份，否则前端换一个key就可能被当新回答。Report自动retry复用generation，用户明确regenerate才是新一轮，旧current在完整成功前继续有效。我保存失败attempt和真实Provider信息，避免重跑后把过去改写成成功。代价是历史管理和部分重复推理，但用户已经成功的成果不会被下游错误破坏，也不会靠默认分或删除证据校验伪造完整流程。

**Level 3：** generation/key重用、失败Answer、Attempt history、短事务publish与单事务approve。下钻28第8/12节。

## 19. 三十个设计追问与推荐回答

这一组偏设计理由；28号的50题用于补实现细节。每题先理解取舍，再按面试深度缩短。

### 19.01 为什么不用一个超级 Agent？

推荐回答：一个Agent能生成所有文本，但不适合拥有所有业务权限。画像处理候选事实，评价处理本轮表现，复盘处理全场综合，写入长期记忆还需要用户授权。我按输入、输出和禁止动作拆角色，让错误可定位、步骤可恢复，再由程序控制发布。代价是调用和编排增加，六角色也不是六种独立模型；我强调职责分离，而不是声称Agent越多效果越好。

### 19.02 为什么评分不交给出题 Agent？

推荐回答：出题关注如何考察，评价关注这次回答覆盖了什么，混在一起容易让一个角色同时定义标准和解释结果。我用独立Prompt、输入输出和调用拆开，让评价不拥有插题或推进权限。这样更易检查与审计，但当前可以使用同一基础模型和Main提供的rubric，所以不保证偏差独立，也没有已标定评分准确率。若继续做，应通过人工标注与独立rubric评测，而非只增加Agent。

### 19.03 为什么 Controller 不也用 LLM？

推荐回答：当前题身份、合法转换、预算和完成条件都是已知规则，不需要语言推断。LLM可以建议追问或结束，但若直接改状态，重试和并发时很难保证只推进一次。我把所有业务转换集中在程序Controller，模型只交artifact，校验后提交。这样状态可查询和故障可恢复，代价是规则及编排复杂，模型觉得合理的动作也可能因预算或版本被拒绝。

### 19.04 为什么不直接用向量数据库匹配全部岗位？

推荐回答：相似度能召回相关文本，但不能证明地区、排除项或资格满足，也不解释候选证据到底支持哪条要求。当前先用关系库的结构条件缩小集合，做资格和证据矩阵，再让模型比较。向量检索以后可作补充召回，不能替代资格和最终政策。Trade-off是当前字面规则较保守、同义表达可能漏匹配，但没有把语义接近误当成可申请或已经具备能力。

### 19.05 Hard Constraint 与 Fit 为什么不能合成一个分？

推荐回答：两者回答不同问题。Fit高说明材料和岗位有相关支持，但明确地区不符或用户排除仍然不应被推荐。合成单分会让技术优势抵消硬性不满足，也会隐藏未知条件。我先判断资格，再评价证据适配，不满足单独排除、未知明确保留。代价是结果不如一个总分简洁，但用户能知道是资格问题、证据缺口还是推荐偏好，不被高分误导。

### 19.06 UNKNOWN 为什么不能当 SATISFIED？

推荐回答：未知是数据边界，不是低一点的满足。当前没有可靠学历、专业和毕业年份结构字段，不能凭简历自由描述或Memory猜。我保留UNKNOWN，允许它作为有提示的探索候选，但模型不能改成满足。继续完善时应让用户明确确认结构化资格，并版本化输入。当前接受推荐较保守的代价，因为错误的资格肯定比明确提示缺信息更容易误导求职者。

### 19.07 为什么不展示精确匹配百分比？

推荐回答：当前匹配是资格规则、材料证据和候选内排序，不是用录取结果训练并校准的概率模型。展示87.43%会制造不存在的精度，而且用户可能理解成录取概率。我使用受证据上限约束的等级，另展示支持、缺口和未知条件。代价是没有一个看似直观的数字，但解释更诚实。如果未来要概率，需要定义目标、收集真实结果并评测校准，不能把模型主观分数直接转百分比。

### 19.08 为什么要 Profile，而不是每次读取简历？

推荐回答：重复解释整份材料，会让推荐和面试对同一人产生不同事实，用户也难纠正。我建立带原文证据的统一Profile，让项目、经历和技能成为后续共用材料，同时保留Resume。修正产生完整新版本，历史面试固定旧输入。Trade-off是增加抽取和存储流程，当前也较保守，但它把事实形成与事实使用分开，后续模块不用各自重新判断整份简历。

### 19.09 Evidence State 为什么允许程序降级？

推荐回答：这是证据支持等级，不是主观熟练度。模型可能把一次使用说成强证据，但引用数量和具体使用位置可以程序检查。我让模型提出状态，程序计算最大支持，最终取较低值，只降不升；未知引用和无支持事实仍拒绝。真实Redis案例从强证据降到已展示。代价是切分和字面规则可能保守，但没有通过取消validator来掩盖模型过度判断。

### 19.10 Evidence 跟普通 citation 有什么不同？

推荐回答：citation常是结果旁边展示出处，我把证据身份纳入写入规则。程序先建立原文片段和位置，模型只能返回已有ID，resolver核对本次范围并回填excerpt。候选事实、岗位要求和表现评价分别有来源，不混为一种事实。这样可以拒绝虚构引用，但合法ID仍不能保证完整语义蕴含，当前Profile支持校验也比公共要求严格，不能说所有内容被绝对证明。

### 19.11 没有技能 Evidence，为什么不说用户不会？

推荐回答：系统掌握的是当前材料，不是用户全部经历。简历没写Kafka只能说明材料缺证明，用户可能会但没写，也可能需要准备，程序不能选择其中一种推断。我用NO_EVIDENCE和待补信息表达边界，面试再产生本轮表现观察。Trade-off是结论不像能力打分那么直接，但避免简历遗漏变成永久负面标签，后续可通过用户确认补充事实而不是让模型猜。

### 19.12 画像或 JD 更新，正在面试为什么不更新？

推荐回答：同场前后必须在同一背景下解释，否则用户更新简历后前面的问题和后面的评分就可能采用不同材料。我开场固定Profile/JD版本及实际题目内容、依据与Memory，后来变化只影响新场。代价是本场不能立即使用新信息，但历史可解释。若用户想基于新材料练习，应显式创建新场，而不是静默替换正在进行的上下文。

### 19.13 为什么 MatchRun 和 InterviewSnapshot 不是同一份？

推荐回答：推荐记录解释当时的输入与排序，面试需要当前可用条件。旧推荐可能关联已关闭岗位、旧画像或旧JD，直接复制会绕过当前检查。我保留MatchRun不变，启动时只带公司和岗位身份，重新按M4规则创建Snapshot。这样兼顾历史解释和新场合法性，代价是两次使用的材料可能不同，需要界面明确这是一场新准备，而非历史推荐逐字重放。

### 19.14 Memory 为什么需要用户确认？

推荐回答：模型看到的是有限场次，很容易把一次回答不足总结成长期标签。我只生成带评价支持的Proposal，让用户批准、修正或拒绝，原提议和确认来源保留。长期写入是授权行为，不是生成行为。代价是多一步操作，但减少错误积累。用户确认也只是自述，不是客观技能认证；因此批准内容仍不能绕过资格规则，面试也不会自动修改Profile。

### 19.15 Observation 为什么与 Profile 分开？

推荐回答：Profile是简历或用户确认支持的相对稳定事实，Observation是某场表现，时间和证据语义不同。本场Kafka回答深度不足不能覆盖“项目使用Kafka”的材料事实。我分开存并在下一场分开输入、独立预算，告诉Agent观察不是稳定标签。Trade-off是上下文分层更复杂，但保留了事实与表现的区别，不把局部失误变成长期能力判断。

### 19.16 Coach 为什么不能重新算平均分？

推荐回答：平均值和出现次数是可计算事实，模型再算会产生第二个数字真相源。我从数据库有效评价计算statistics，Coach只输出定性分析和评价ID，resolver回填支持及次数。这样模型超时也能看统计，重复问题需要至少两条不同有效引用。Trade-off是数字分析表达受限制，但评分与解释清楚分开，不让流畅总结覆盖原评价记录。

### 19.17 为什么 repair 最多一次？

推荐回答：repair是修结构，不是让模型不断改内容直到校验通过。一次约束修复可以处理JSON或Schema错误，同时保护已有事实字符串和引用；再失败就保留错误。无限循环成本不可控，还可能悄悄改事实。Trade-off是部分可修结果也会停止，但失败含义明确。Evidence或业务支持错误不属于这种格式修复，不能自动补新引用来通过。

### 19.18 validator 失败为什么不能 fallback 模型？

推荐回答：合法性失败说明这次输出不满足规则，不等于Provider不可用。自动换模型不断尝试会掩盖问题、改变审计和验收含义。我只在明确model/endpoint不可用、限流等availability错误时fallback；Schema、Evidence、业务错误保留失败，普通timeout也不自动换。代价是成功率看起来更低，但不会用更容易通过的输出代替错误诊断。

### 19.19 SSE 为什么一定在 commit 后发结果？

推荐回答：前端显示评价或完成，用户就认为结果已保存。若先发事件再提交，数据库失败会留下一个看得到却不存在的结果。我先校验和事务commit，再发业务事件，等待中可以先发处理中status。网络断开后凭幂等业务身份重用已存结果。Trade-off是结果要等提交，不能追求更早的假响应；前端还需持续parser处理chunk不等于event的问题。

### 19.20 为什么不在模型调用时锁 Session？

推荐回答：真实模型可能几十秒甚至更久，持锁会阻塞业务并占数据库连接。我先读取固定上下文和状态版本，关闭读取事务，模型回来再短事务锁定并重验。别人已推进就返回conflict，不覆盖。代价是陈旧推理可能浪费token，但比长锁等待安全。这是M4核心的设计，不能泛化成仓库所有Research都已经完全消除长读取事务。

### 19.21 有幂等 key，为什么仍可能重复模型调用？

推荐回答：key和唯一约束保护有效业务结果，两个请求仍可能在第一次发布前同时推理。我用版本/attempt检查拒绝陈旧发布，成功请求复用持久化结果，但不承诺模型计费exactly-once。Matching还有运行lease，其他流程仍有改进空间。继续做可增加generation lease和调用协调，但要先区分“没有重复记录”和“没有重复外部调用”，不能把两者混成一个保证。

### 19.22 Evaluation 失败，为什么不能直接下一题？

推荐回答：下一动作依赖当前评价，如果失败仍推进，就失去本轮闭环，还可能制造报告缺口。当前保留回答与失败审计，使用同一业务身份重试，不补默认3分。预算耗尽则是明确的程序终止，可以没有评分，但要展示未评价，不能称模型成功。代价是用户需要等待或重试，但下游统计、Coach和Memory不会建立在伪造评价上。

### 19.23 FOLLOW_UP 和 DEEP_DIVE 为什么都要预算？

推荐回答：补问和深入都能提高针对性，也都可能让模型无限延长会话。我区分语义和来源：追问补缺口，深挖延伸主题，二者都保存带父题的独立问题，并受根题次数、总题量、轮次、时间和调用reservation限制。Trade-off是可能未问完想问的内容就结束，但过程可预测。当前预算是保守估计，不能说已经精确计量所有实际token。

### 19.24 有 Replay，为什么还要真实模型 smoke？

推荐回答：Replay证明给定输出下业务规则和状态转换正确，不证明真实模型愿意遵守Schema或Provider返回格式兼容。我另用真实DeepSeek运行六角色，让结构、证据和持久化接受真实输出。两者复用同规则，Live暴露的问题再变稳定回归。Trade-off是smoke成本与场景有限，不能替代线上效果评测；Fixture数据与真实模型模式也必须分别标记。

### 19.25 为什么不另写一套 mock business flow？

推荐回答：另写mock流程容易跳过Controller、resolver和数据库约束，看似跑通却没有验证最危险的路径。我只替换Provider结果，仍执行同一事务、审核和发布过程，才能检查故障注入时是否rollback、重复请求是否复用。代价是测试环境需要真实数据库和更多准备，但固定外部依赖让回归稳定，也不会把演示用的成功故事误当作领域逻辑正确。

### 19.26 Live Search 不稳定，项目链路怎么成立？

推荐回答：用户主流程本来就不依赖每次搜索，它使用公共库已有可用数据。Research是离线供给侧，当前上游搜索受CAPTCHA和限流影响，稳定测试/Demo使用明确Fixture，不伪装Live。真实模型能力另做验收。Trade-off是岗位覆盖不能宣传完整，也不能说全自动搜索已稳定。继续做应建设合法稳定数据源、审核与更新观测，不把求职产品变成反爬工程。

### 19.27 公共数据与用户数据为什么严格分层？

推荐回答：公共JD说明岗位要求，私有简历说明候选材料，评价说明本场表现，三种事实不能相互证明。公共公司、岗位和题目可共享，Profile、面试、Memory按用户授权隔离，Matching只建立双方支持关联。这样避免JD要求被推成用户技能，也避免原始未审核内容直接给用户。Trade-off是关联和provenance更复杂，但权限与解释都清楚。

### 19.28 为什么先用模块化单体而不是微服务？

推荐回答：当前是本地验证阶段，核心难点在状态、证据和事务，不是服务数量。模块化单体便于让画像发布、评价推进和Memory审批保持明确短事务，同时把文件/模型/搜索封装为Provider，Worker处理重任务。代价是扩展和故障隔离有限，但提前拆微服务会增加跨服务一致性成本。以后应按实际瓶颈拆，而不是为架构名词拆。

### 19.29 怎么证明项目有效，只有测试数够吗？

推荐回答：测试数只说明已定义行为被检查，不证明求职效果。我分开验证规则、真实模型和用户流程：Replay检查并发、引用、事务，真实DeepSeek检查输出能通过约束并落库，浏览器检查交互与刷新。当前可以说核心可运行，不能说提高录取率或评分准确。继续需要人工标注评分、推荐解释评测和真实使用反馈，再用明确指标评估产品价值。

### 19.30 如果继续做，优先升级什么？

推荐回答：我会按用户主线和已暴露风险排序，先改善慢模型的等待/恢复体验、保守token预留和重复调用协调，再补可靠结构化资格、解析覆盖及公共发布衔接，最后做部署安全和负载评测。每项都应保留Evidence与授权边界，不通过弱化validator追求通过率。当前只是未来方向，没有新功能授权，也不会把未实现的分布式能力写进简历。

## 20. 项目不足怎么自然回答

### 20.1 Live Search

“当前不把Live Search作为稳定演示，因为上游限流和验证码不是业务状态机能解决的。用户主线读取已发布公共库，Fixture明确标记。下一步会考虑合法稳定源、刷新观测与发布衔接，但现在不宣称搜索稳定完成。”

### 20.2 OCR 与解析覆盖

“我复用原上传/解析链，当前更适合可提取文本的材料，扫描件OCR、DOCX表格和可靠页面位置还有限。这个阶段先确保事实引用不造假，无页码就留空。继续做会增加保留位置的解析和质量检测，而不是让模型猜原始文本。”

### 20.3 资格 UNKNOWN

“学历/专业/毕业年份现在经常未知，是因为没可靠结构字段，不是我把它当满足。当前接受保守结果，避免推荐假确定性。以后让用户明确确认资格并固定版本，不能拿自由Memory当证明。”

### 20.4 Token budget

“目前预算采用保守字节reservation，不是精确tokenizer，真实验收甚至短面试也出现提前结束。我保留该场记录，没有改Controller刷过。未来会分清预留和实际usage、调用后对账，降低过度预留，同时保留总预算约束。”

### 20.5 模型延迟

“DeepSeek Matching实际有超过100秒的请求，所以不能说实时低延迟。现在具备超时、审计和安全retry，继续会考虑异步生成、进度/恢复体验和输入压缩。性能改善要实测，不预先写百分比。”

### 20.6 并发规模

“我验证了特定并发冲突和事务rollback，但没做大规模用户压测。当前guard是进程内，幂等发布也不等于一次模型调用。下一步是分布式限流、generation协调和负载测试，不把数据库不变量当吞吐证明。”

### 20.7 推荐覆盖和公共发布

“当前literal矩阵很保守，Research质量批准与用户可用PUBLISHED之间也不能自动画等号。这个阶段优先明确来源与审核，不宣传持续自动招聘库。后续会完善发布规则和受验证topic归一化，扩大覆盖但不能编技能。”

### 20.8 生产验证与 Milvus

“项目完成本地Runtime和真实模型核心验收，还没有真实用户规模、评分标定和生产SLO。Milvus在既有知识检索中有作用，新主链主要是固定关系数据，不为了技术栈好看说全流程RAG。后续要补监控、安全部署、人工评测和备份恢复演练。”

### 20.9 证据校验的上限

“当前能验证引用和一些支持规则，不能证明所有语义蕴含或模型评价客观准确。Safe Fetch也有DNS校验与连接绑定的改进空间。我会把机制和保证范围分别说清，后续增加支持规则和对抗安全测试，不用‘彻底防幻觉’或‘绝对安全’概括。”

## 21. 最终主故事线（5–8 分钟口述）

以下是一条连续主线，按正常面试语速练习并计时；可删除一段而不破坏逻辑。时间是目标，不是要求逐字背。所有“我”仍须符合本人实际参与。

我做的是面向秋招的多Agent求职与模拟面试平台。出发点是把求职准备连成一个有依据的过程：简历不能只上传后放在那里，岗位要求也不应该只是复制给模型，做完模拟面试以后，用户需要知道下一步练什么，同时不被一次表现永久贴上能力标签。

单纯聊天也能问问题，但缺少稳定业务过程。它不自然知道当前哪题有效、回答是否重复提交、评价失败要不要继续，更不适合凭一段总结直接改长期记忆。所以我把项目的中心定为画像、岗位、面试和复盘之间的数据连接，而不是只追求生成看起来合理的对话。

第一步是Candidate Profile。我保留原有上传、文件存储和解析，增加一个统一候选材料层。技能、项目、教育和工作都引用原简历依据，未知内容明确留下。这样推荐和面试使用同一份事实，不各自重新解释整份简历。用户能修正，但形成完整新版本，不覆盖旧版本；后面历史面试也能解释当时用的是什么材料。

第二步是岗位匹配。我没有让模型面对全库岗位打百分比分，而是先程序做有限召回、资格检查和证据矩阵。矩阵回答的是某条要求有没有候选事实支持。明确不满足的岗位排除，学历等缺少可靠字段就保留未知，偏好Memory也不能用来补资格。模型只能在提供的集合内排序、选择已有支持关联，程序再合成最终顺序。代价是保守，但避免把语义相关包装成资格满足。

第三步是核心面试。我把出题和评价分成两个角色：Main负责如何问和追问内容，Evaluator只看本轮回答、问题和rubric，给五维评价及动作建议。独立的是职责，不是说使用两种模型就保证评分无偏。所有业务推进都交给程序Controller，它检查当前题、来源、预算和状态，才决定补问、深挖、下一题或结束。

这里有两项关键工程机制。一是开场固定Profile、JD、公共题实际内容以及Memory，不能面试到一半静默换底稿。二是模型很慢，所以不拿着业务锁等它：读状态版本，调用模型，回来再短事务检查版本和当前题。如果别人已推进就冲突，不覆盖。回答有幂等身份，评价失败不默认给3分也不直接跳题；结果要等数据库提交成功才发给前端。这样聊天内容和真实过程有清楚边界。

面试结束后，统计和分析也分开。五维均值、有效评价数量从数据库计算，Coach不能重新评分。它只引用本场真实评价做优势、问题和准备计划。重复问题至少两条不同有效评价支持，出现次数由程序数。Coach失败不会回滚已完成面试；新报告完整成功才替换旧current，失败历史保留。

长期Memory是最后一道边界。某场Kafka回答深度不足，只能先成为本场Observation，不能直接写用户Kafka很差。模型可以提出带依据的记忆建议，用户批准、修正或拒绝，批准后的内容才进已有长期Memory。下一场也把用户确认的记忆和近期观察分开，分别预算并固定。我没有让评价自动修改Candidate Profile，因为稳定事实和某次表现不是一种东西。

贯穿这些设计的是Evidence grounding。候选材料和公共来源各有依据，程序先建立可引用片段，模型只选择已有ID，excerpt由程序回填。Matching连接双方依据，Interview固定来源，Report引用本场评价。它能约束一部分幻觉，但不是证明所有语义真实，所以我一直区分没有证据和用户不会。

验证上我做了两条路径。Replay只替换外部Provider，仍走相同validator、Controller和事务，能重复检查失败、重试与并发边界。之后用真实DeepSeek运行六个正式角色。数据仍是明确的本地Fixture和固定回答，Live Search受上游限制继续冻结，不能把这次说成全部联网真实招聘验收。

真实测试里最有价值的发现是Profile技能状态过高。结构已经合法，但业务Evidence不支持。我没有删validator，而是让模型提状态，程序算最高支持，只向下收敛。DeepSeek把Redis提成强证据，程序根据一条实际使用依据降到已展示。六角色后来都成功，旧失败、超时和预算结束场次没有删。这让我更明确：能确定性计算的字段，不应该通过更长Prompt完全寄希望于模型。

最后项目得到的是一条能连接材料、岗位、练习、复盘和受控记忆的本地可运行链路，有Replay和真实模型两种证据。它还没有大规模生产或真实录取效果验证，解析、资格覆盖和模型延迟也有边界。如果继续做，我会优先改善恢复与等待体验、可靠结构化输入和生产观测，而不是继续加Agent。最核心的经验是：把模型生成、程序规则和用户授权分清，比让一个模型做更多事情更重要。
