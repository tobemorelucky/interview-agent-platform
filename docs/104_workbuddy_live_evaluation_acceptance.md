## 2. 六份实际提交的回答（与冻结文本逐字一致）

**RAG-B1（88 字，GOOD_SHORT）**
> 用 RRF：每路按名次取 1/(k+rank) 再累加，k 取 60 左右。它只看名次，所以不用把 BM25 和余弦归一到同一尺度；代价是丢掉分数幅度，k 和截断深度要自己定。

**RAG-A2（316 字，POOR_LONG_WRONG）**
> 混合检索的融合我一般分两步。第一步把两路分数归一化，因为 BM25 和余弦相似度都是 0 到 1 之间的分数，量纲本来就一致，所以直接加权求和就可以：final = 0.5 * bm25 + 0.5 * cosine。第二步如果效果不好就上 RRF，RRF 的做法是把两路分数先相加再取对数，也就是 log(bm25 + cosine)，这样能把高分段的差异放大。RRF 的优点是完全不需要调参，k 固定 60 就行，而且 k 越大越偏向头部排名，越容易把最相关的结果顶上来。缺点是计算量比加权求和大一点。实际项目里我用 RRF 之后 top-k 命中率大概提升了三成，因为 RRF 一定优于加权求和，任何场景都应该优先用 RRF。

**LG-B2（116 字，PARTIAL）**
> LangGraph 用 StateGraph 管理状态，节点函数读 state 返回更新，条件边可以控制走向。持久化用 checkpointer，不过我一般把它当可选优化，不开也能跑，开了主要是方便调试。恢复的话重新跑一遍图就可以。

**LG-C1（189 字，NEAR_MISS）**
> StateGraph 声明共享 state，节点返回增量更新，reducer 决定合并；条件边支持分支与循环。checkpointer 在每个 super-step 后保存快照，用 thread_id 关联，所以能断点恢复和人工介入。checkpoint 是状态快照不是业务事务，外部副作用要幂等。补充一点：checkpointer 是在节点函数内部、节点逻辑执行前写入快照的。

**KF-A1（229 字，GOOD_FULL）**
> Kafka 只保证至少一次，所以去重必须落在业务侧。用订单号加事件类型做幂等键，在同一个数据库事务里先写去重表（唯一约束），冲突就说明这次是重复投递，直接跳过；没冲突就更新订单状态，两者同一事务提交。处理成功后手动提交 offset，关掉自动提交，避免业务没提交但 offset 已提交导致丢消息。还要注意 offset 提交与业务事务之间的窗口：业务提交成功、offset 未提交时重启会重放，这时靠幂等键兜住。重试多次仍失败的进死信队列并告警，人工补偿。

**KF-A2（253 字，POOR_LONG_WRONG）**
> Kafka 默认就是 exactly-once，所以消费端不用额外做去重，只要把 enable.idempotence 打开、offset 用自动提交就行，消息只会被消费一次。如果还是出现重复，用数据库自增主键就能自动去重，因为每条消息插入时主键不同，重复的会插入失败直接跳过。另外 offset 提交和业务事务是两个独立的东西，先提交 offset 再处理业务更安全，因为这样不会重复消费。消费失败的话把 offset 回滚到上一条重新消费即可，Kafka 支持 offset 回滚，所以不需要死信队列。

## 4. 每份回答的实际评价理由（模型原文，未改写）

### RAG-B1（19/25，tc=4）
> 回答准确说明了 RRF 的核心公式（1/(k+rank) 累加）、k≈60 的常用取值，以及"只看名次、无需跨尺度归一"的好处，并点出丢弃分数幅度、k 与截断深度需自定的代价，机制层面正确。但覆盖不足：未说明 k 越小越偏向头部排名的方向性影响，也未提及弱相关但排名靠前的结果会被抬高这一具体风险，更未给出用标注查询对比融合前后 Recall@k / nDCG 的验证方式。属于机制正确但边界与验证维度不完整的部分覆盖。

### RAG-A2（9/25，tc=1）
> ……但核心技术机制几乎全部错误：RRF 被描述为"先相加再取对数 log(bm25+cosine)"，实际是按名次累加 1/(k+rank)；声称 BM25 与余弦相似度"量纲一致、0 到 1 可直接加权"不成立（BM25 无上界、余弦可为负）；k 的方向说反（k 越小越偏向头部排名）；"k 固定 60 不用调参""RRF 一定优于加权求和、任何场景优先用"属于绝对化错误结论；所谓"命中率提升三成"缺乏可验证的评测口径。

### LG-B2（12/25，tc=2）
> 回答正确点出 StateGraph、节点读 state 返回更新、条件边控制走向，方向对。但把 checkpointer 说成"可选优化、不开也能跑、主要方便调试"是明显误解：checkpointer 是断点恢复、thread_id 关联、人工介入的基础，不是调试附属品。恢复说成"重新跑一遍图"也回避了从快照恢复的机制。完全没提 reducer 合并语义、循环终止条件、checkpoint 与业务事务的区别、外部工具副作用幂等/补偿。属于部分覆盖、关键机制缺失。

### LG-C1（17/25，tc=3）
> ……主干机制基本准确。但存在一处明确事实错误：称 checkpointer 在节点函数内部、节点逻辑执行前写入快照，与 LangGraph 在 super-step 边界（节点执行完成后）保存 checkpoint 的机制不符。此外未说明循环的终止条件或最大步数控制，恢复后重复执行的具体防护（幂等键、补偿）也只点到未展开。

### KF-A1（24/25，tc=5）
> 回答准确覆盖了当前问题的核心机制：Kafka 至少一次语义、业务侧幂等键（订单号+事件类型）加唯一约束、去重记录与订单状态更新同事务提交、关闭自动提交并在处理成功后手动提交 offset、offset 与业务事务之间的重放窗口由幂等键兜底、反复失败进死信并告警补偿。机制表述正确，步骤清晰，异常流向明确。深度上对重放窗口有解释，但对并发重复投递的竞态（唯一约束冲突后的处理路径、事务隔离级别影响）以及死信队列的幂等与补偿细节未展开。

### KF-A2（7/25，tc=1）
> ……核心技术判断几乎全部错误：把 Kafka 默认语义说成 exactly-once、认为开启 enable.idempotence 即可让消费端只消费一次、认为自动提交 offset 更安全、认为先提交 offset 再处理业务不会重复消费、认为数据库自增主键能对业务消息去重、认为 Kafka 支持 offset 回滚到上一条。这些都与 Kafka 至少一次语义、幂等生产者仅作用于生产端、offset 提交与业务事务的窗口关系相悖。

### 5.3 一处必须点明的评分缺陷：技术分被覆盖缺口扣分

`ai_agent_application` 的技能锚点写的是：

- `technical_correctness`：**机制和术语是否准确**，是否区分模型与程序责任
- `coverage`：是否覆盖当前问题要求的链路与关键步骤

RAG-B1 的每一句话都成立（公式、k≈60、只看名次、丢幅度、参数要定），但 tc=4，且评语给出的理由全部是"未说明…未提及…未给出…"。这是把 coverage 的缺口重复扣到 technical 上。上一轮 G3 GOOD（19/25，tc=4）是同一模式；本轮 KF-A1（tc=5）没有复现，说明它依赖具体措辞，不是稳定规则，但确实存在。

影响：正确但简短的回答会被压 1～2 分，且这一分与"答错"同属一个维度，会让"简短正确"与"有轻微技术错误"在分数上难以区分。

### 5.4 另一种模式：中间档位的五维同步抬升

LG-B2（2/2/2/3/3）→ LG-C1（3/3/3/4/4）：五个维度全部 +1。这更像是"整体档位 +1"，而不是五个维度各自判断的结果。上半段的 RAG、KF 两组则出现了维度内差异（19 的 4/3/3/5/4、24 的 5/5/4/5/5），说明模型并非只会整体平移，但在两个质量接近的中间样本上倾向同步调整。

- 2 次额外 HTTP **都是合法结构化修复**：`EVALUATION_QUOTE_SUBSET_V1`，原因是模型给出了 5 条逐字引用，而 `KnowledgeObservation.answer_quotes` 的 `max_length=3`，修复要求从已有引用中选 3 条；`validate()` 断言除引用外其他字段未变。两次修复都成功（`structured_retry=1`）。

### 7.1 本轮发现的账本归属缺陷（我的夹具问题，已修）

第一次写脚本时，`model_scope` 在**开会话**时设置。同一对的第二个会话会覆盖第一个的值，于是**同一对的两份回答都记到了第二个用户头上**（账本里 user:2 承担了 RAG 两份、user:4 承担了 LG 两份、user:6 承担了 KF 四份）。金额与状态没有错，错的是 `owner_key` 的可读性，导致"评价 ↔ 账本"只能靠 token 总数与时间顺序对应，而不能靠 owner 直接对应。

- 已修：`model_scope` 改到**每次提交前**按该样本的 user 设置。
- 已离线验证：新增 `--evaluation ledger` 模式，用 `LedgerProbe`（真实 `governed_call` 准入/结算网关 + 固定回复，**0 HTTP**）跑一遍。结果：6 次提交 → 6 条 admission，owner 分别为 user:33…38，route 均为 `answer_evaluation`，全部 SETTLED、各 1,500 tokens；重复提交未新增 admission。证据见 `r25_ledger_probe.json`。
- 真实那 6 条评价不受影响：它们由真实模型产出、真实落库，只是账本的 owner 标签错位，已在 §7 表内按 token 与时间还原。

### 7.2 一个产品侧可审计性问题（未改代码）

`governed_call()` 在 `model_scope` 未设置时回退到 `user:{uid}` + route `legacy_llm`，并用 `db.session.async_session_factory` 作为账本库。全仓库 `model_scope.set(...)` 只出现在 `job_target/service.py`、`public_career/research/audit.py` 与简历侧 provider，**`modules/interview` 与 `api/` 都没有设置**。

后果有两层：
1. 线上真实评价的 admission 会被记成 `route=legacy_llm`，而不是 `answer_evaluation`。这不影响额度与结算，但"按 route 统计评价成本"会失真。
2. 对任何外部夹具（比如本轮）来说，回退目标指向 `.env` 里的正式库；若不显式设置 scope，测试账本会写进正式库。本轮脚本显式设置了 scope，因此账本只落在 sandbox。

本条按"只测试、不改产品代码"的要求，仅记录，未修改。
