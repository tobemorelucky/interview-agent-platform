# 秋招口述材料：自适应面试官与长期能力记忆

定位：个人完成设计与迭代的 AI 应用工程项目，不是生产规模平台。设计讨论可说“我设计/我选择”，具体协作方式如被问及应如实说明使用 AI 辅助编码与测试。以机制、真实故障和验收为主，不背类名。源码对应表见09文档。

## 一、30 秒整体介绍（约 30–40 秒）

我做的是面向秋招的多 Agent 求职与模拟面试平台，从简历画像、岗位匹配一直到面试、复盘和下一场训练。它的重点不是聊天，而是把模型决策放进可验证的业务流程：简历事实必须有原文证据，面试官自主选择追问目标，程序控制题源、预算和状态；长期记忆根据多场表现重算，区分提示后答对与独立验证，并且不会把推断偷偷写成简历事实。

## 二、3 分钟整体介绍

我最初想解决的是，很多模拟面试产品只是根据简历生成一串问题，用户答完后收到一个分数，但下一次还是从头开始，也很难解释问题和评价依据。

所以我把平台做成一个求职准备闭环。简历上传后先形成有证据的候选人画像，结合已审核的岗位资料进行匹配，用户选岗后创建面试，回答经过独立评价，最后产生报告、训练建议和可控记忆。架构上仍然是六个模型角色，没有为了“多智能体”不断加 Agent。后端用 FastAPI 和 PostgreSQL 管业务状态，Redis 配合队列和协调，公共资料重任务走既有 Worker，在线面试则采用有超时的同步异步调用，而不是把所有任务都塞进 Celery。

这里我比较重视三条边界。第一是事实边界。Profile 早期让模型生成事实描述，即使意思合理，也可能无法满足原文字面证据校验。我后来把它改为选择和分类已有 Evidence，稳定事实文本由程序从原文构造。岗位推荐也不是编一个匹配百分比，而是显示岗位要求对应哪些候选事实，哪些没证明，以及程序判断的硬资格。

第二是面试决策边界。Main 负责根据当前回答和缺失机制选择追问、举例、深挖或换题，Evaluation 独立评分。Main 不是想引用哪个题源都可以，程序根据冻结 Blueprint 生成合法目标与题源组合，模型只能选择一个组合。Controller 再检查当前会话版本、预算和引用，最后原子提交评价、知识状态和下一题。这样既保留模型自主性，也不把数据库控制权交给它。

第三是长期记忆边界。我没有单独加 MemoryAgent，而是根据已完成面试的真实观察重算能力状态。追问之后答对不等于独立掌握；同条件表现相反先标冲突，旧判断太久没验证进入待复测，而不是偷偷扣旧分。下一场把少量相关知识点冻结成记忆计划给 Main，但 Evaluation 看不到这些历史弱点，避免先入为主。

工程上我遇到过题源组合错误、模型长推理却不输出正文、评价成功但下一题失败等真实问题，针对它们补了事务、审计复用和恢复测试。当前完整规则闭环通过了隔离 PostgreSQL 与浏览器 Replay，真实 DeepSeek 也验证了两组记忆决策：已验证 Kafka 后选择 Redis，Kafka 存在冲突时主动问崩溃恢复。我要强调，那是真实模型的有限决策验收，不是宣称已经跑完完整多场 Live 或达到生产规模。

## 三、5 分钟：V2.1 自适应面试官

以下可按五个段落展开，语速和追问会影响时长，不需要逐字背。

### 0:00–0:55 为什么不继续固定 Workflow

最初我的面试流程更像评价驱动的 Workflow：评价建议下一步，程序据此决定追问或下一题。这种方式可控，但面试官对“接下来验证什么”的自主性不明显。我希望保留可靠的状态机，让 Main 能根据真实回答决定考察目标，而不是只改写题库内容。

我没有新增 Planner Agent，而是把策略选择和问题生成放在同一次 Main 调用里。现在的实际策略是 FOLLOW_UP、REQUEST_EXAMPLE、DEEP_DIVE 和 NEXT；我不会把还没做的挑战、场景模拟能力都说成已经完整实现。题目来源包括固定 Skill、岗位要求、简历事实和合法公开题源，不同来源的可信语义也不同。

### 0:55–1:55 模型到底能决定什么

创建面试时，我先固定目标岗位、JD、ProfileVersion、Skill、轮次、风格和 Prompt 版本，再构建 Blueprint。每轮给 Main 的不是开放数据库，而是当前合法目标、历史问题、本轮回答、评价缺口和知识状态。已经得到充分支持的目标不再机械重复，连续追问和主题冷却由程序计算。

比如候选人只说“Kafka 失败重试，成功后 ACK”，Main 可以追问 ACK 与事务的先后、要求具体举例，或者深挖重复消费，不应随机转去问学校。模型有自主选择权，但不能自行判定剩余题目数量，也不能直接把 Session 标成完成。五维分数同样由独立 Evaluation 产生，不由 Main 为自己的提问效果打分。

### 1:55–3:00 一个真实失败带来的契约调整

这里最值得讲的是 UNKNOWN_DIRECTOR_SOURCE。早期让模型分别返回知识点 ID 和题源 ID，两个字段各自合法不代表组合合法。真实验收出现过 HTTP200，但业务拒绝，说明 JSON 正确并不等于业务正确。

我没有扩大白名单或自动换题源，而是让程序从冻结蓝图生成合法组合，模型选择一个稳定的 C_* ID。这个 ID 由蓝图指纹、目标和固定来源计算。相同题源关联多个知识点时，各自是明确的不同组合。程序只还原模型选中的组合，然后继续校验题目、来源、事实证据和难度。这样把引用一致性变成结构化选择，同时保留模型对目标与策略的决定权。

Controller 在提交时还会用当前会话版本重算合法空间，防止生成期间另一个请求已经改变活动题。这不是“给 JSON 加几个 enum”，而是模型选择与服务端业务提交之间的一份契约。

### 3:00–4:05 事务、失败恢复和成本

一次回答先保存 Answer 和幂等键，再释放事务调用 Evaluation 与 Main，最后进入短事务提交 Evaluation、知识状态和下一题。我不在等待模型时持有业务行锁。提交时核对 state_version 和 active_question_id；重复请求使用原键，不重复生成有效 Answer。

如果 Evaluation 成功但 Main 失败，正式评价和下一题不能提交一半。成功的评价审计可复用，但要求同一场次、Answer、输入指纹、模型和 Prompt，复用后也重新验证。这减少了安全重试时重复评分的成本。超时、取消和未知 usage 不能按零处理；会话预算和用户额度分别结算。SSE 展示阶段，但不能以“发过一个事件”代替事务完成。

### 4:05–5:00 如何证明与不足

我先用固定 Replay 验证不同回答产生不同合法策略、非法组合被拒绝、并发与失败恢复，再跑隔离 PostgreSQL 和真实浏览器。之后有限调用 DeepSeek，两个专业场景都通过了组合解析与 Controller 提交，没有再出现原来的题源错误。

这个验证不证明模型永远问得好。程序能严格验证引用和状态，不能完备判断中文题意；Live 的下一步恰好都选 FOLLOW_UP，不能据此说四种策略都真实测完。我的工程取舍是把能确定的约束交给程序，把开放语义留给模型，并用真实失败记录说明边界，而不是为了演示把结果替换成固定成功案例。

## 四、5 分钟：V2.2 长期能力记忆

### 0:00–0:55 为什么不是多存一段聊天总结

做完动态面试后，我发现“记住用户上次答得不好”很容易实现，但有三个风险：提示后答对被当成掌握，一次失误覆盖过去表现，以及历史弱点反过来污染下一场评分。因此我把记忆拆成两条路径：用户确认的目标、偏好仍走原提案审批；系统对技术表现的推断另有状态和来源，不能成为简历事实。

这里没有新建一个 MemoryAgent。简单时间判断、去重、冲突和状态重算用程序更可解释，也不需要每轮多花一次模型请求。模型的职责是对当前回答做知识诊断，程序判断这些观察是否有效、是否独立，以及如何影响下一场规划。

### 0:55–2:00 原始观察与状态怎么形成

能力来源不是历史总分，而是已完成 Session 中真正提交的 Evaluation 和知识观察。服务核对用户、问题、回答、消息、Snapshot 和 Blueprint 的关联，还确认引用片段确实来自本次回答。只要会话未完成、评价没提交，或引用无效，就不能进入长期聚合。

状态包括未知、疑似缺口、练习中、已验证、待复测和有冲突。只有引用充分、没有开放缺口和争议的独立表现才算支持。追问或深挖会暴露提示，保守算有辅助；同一场答对多次也不能冒充跨场验证。至少两场独立支持才可能已验证，而不是把平均分超过某个值当作掌握概率。

演示里第一场 Kafka 回答缺少机制，第二场追问后补齐仍是练习中；第三场独立答对只得到一次支持，第四场才到已验证。每一步都能回到具体 Evaluation，而不是只展示一条生成式总结。

### 2:00–3:05 遗忘和冲突怎么处理

遗忘也分两件事。一是很旧且不相关的记忆不必一直进入 Prompt；二是旧能力结论需要重新验证。我没有降低过去分数，而是根据验证次数和语境设置30、60、90天的复测窗口，时间可以注入测试。这里是可解释规则，不是学习科学结论。

冲突不能只按先错后对、先对后错做字符串比较。我用岗位、轮次、难度、来源、题干和评分要点形成严格的语境指纹。同条件独立正确后又出现相反表现，先保留冲突；不同语境的表现只标差异。之后两场同条件独立复核可以解决冲突，但原记录不删。代价是不同措辞的语义等价场景可能识别不到，我宁可暂缓判断，也不使用模糊匹配误报矛盾。

### 3:05–4:05 用户控制和下一场联动

用户可以排除有争议的评价或撤销推断。服务检查归属与 revision，排除列表进入聚合输入，撤销是持久标记，不能因为报告 regenerate 就复活。当前版本没有撤销恢复按钮，也不允许用户直接点选“我已掌握”来制造验证证据。

创建下一场时，只把 Blueprint 相关的少量记忆变成 MemoryGuidedPlan，包含状态、历史缺口、建议验证意图、优先级和来源版本。Main 仍从合法组合中决定考什么；记忆不能增加题源权限。计划一旦进入 Snapshot 就冻结。本场期间即使用户更正历史，也不会悄悄改变正在进行的面试；更正影响之后的新场次。

同时，我专门从 Evaluation 输入移除了历史能力推断与风格信息。Main 可以知道需要验证 Kafka，但评分 Agent 只能根据这道题、当前回答和岗位依据判断，不能因为“这个人以前弱”就扣分。

### 4:05–5:00 工程验证与真实边界

聚合在用户级 PostgreSQL 事务锁下读取有效观察并重算，输入指纹没变就不加版本，完成场次时与原事务一起提交。这样并发完成、报告重生成和重试不会把同一观察重复累计。当前重算不是无限可扩展，长历史有性能成本，我没有做生产规模压测。

真实 DeepSeek 验收里，A 的 Kafka 已有两次独立支持，Main 选了 Redis；B 的 Kafka 有冲突，Main 主动问业务成功但 offset 未提交时宕机的恢复问题。四次 Main 请求确实带记忆计划，两次 Evaluation 没有。整批六个请求、35,585Token。它证明了 Replay 历史与 Live 决策能够接通，不代表完整多场 Live 的长期效果或因果提升百分比。对个人秋招项目，我希望展示的是完整可追溯的工程闭环，而不是夸大算法创新。

## 五、24 个技术追问与参考回答

### 1. 你的“多 Agent”是否只是六个 Prompt？

每个角色确实是通过受控模型调用实现，不是六个长期自主进程。价值在职责、输入输出和反馈闭环：Research 产出审核资料，Profile 产出有证据事实，Matching 产出推荐，Main 与 Evaluation 交替，Coach 产出复盘与提案；程序管理状态。不要声称 Agent 自由互聊或自动协商。

### 2. 为什么不加独立 Planner？

当前一次 Main 调用同时输出策略与问题，Director 是内部决策组件。额外 Planner 会增加延迟、预算和规划—执行一致性问题。现有候选空间足以支撑任务，不需要为了角色数量增加调用。复杂工具规划未来有需求再评估。

### 3. 如何保留自主性又不让模型乱操作？

程序计算合法目标、来源、策略和预算空间，Main 在其中选择并生成措辞；Controller 重新校验并提交。模型可以决定追问什么，但不能改数据库、自己结算Token或将来源外推给别的目标。

### 4. C_* 为什么比 target/source 两个字段更可靠？

Schema 无法保证两个独立合法 ID 之间关联正确。组合 ID 把关系变成受控选择，包含蓝图/目标/来源身份；模型少写复杂 ID，程序精确还原。仍需业务验证，不能说 JSON Schema 就解决了语义正确性。

### 5. 同一题源支持多个知识点怎么办？

每个明确关联生成自己的组合。共享来源不等于全局授权，也不能凭主题相似随便引用；新蓝图或来源版本变化后旧组合不能继续使用。相关测试在 Director contract 专项中。

### 6. Main 选合法组合就能保证题目正确吗？

不能完备保证。程序验证目标主题、来源与事实引用、题型、难度，能拒绝不少错误，但自然语言是否高质量仍需场景评测和人工检查。历史 Live 验收因此同时核对问题内容，不能只看 HTTP200。

### 7. 为什么知识诊断不直接使用五维均分？

均分掩盖具体机制差异，也无法区分是否提示。能力观察必须给当前 knowledge_id、回答原文片段、缺失机制和已解决缺口；程序校验后才入本场账本。总分仍用于本场报告，不直接转成掌握认证。

### 8. 两次独立验证如何定义？

至少两个不同已完成 Session，各自包含充分引用、没有开放缺口和争议的表现；问题是 NEXT 且没有 guidance 才保守视为独立。FOLLOW_UP/DEEP_DIVE 都可能受启发，不算独立。这是保守工程口径，不是考试理论的绝对定义。

### 9. 提示后答对有没有价值？

有，它可说明练习进步，但不能直接提升到 VERIFIED。系统保存 assisted、历史变化与缺口，下一场建议换情境独立核对。这样避免“被问出答案以后立刻宣布掌握”。

### 10. 为什么不是遗忘曲线或分数随时间衰减？

项目没有足够数据校准那类模型。当前仅判断结论是否过时：30/60/90天分级进入 RECHECK_DUE；旧分数和错误原记录不动。另有180天非重点检索过滤，和能力状态时效是两回事。

### 11. 先错后对与先对后错有什么区别？

先错后对可能是正常学习，仍结合独立支持计数；同条件独立正确后独立相反表现先形成 CONFLICTED，不直接覆盖。不同语境的差异不强行当矛盾，辅助后的正确也不抵消独立错误。

### 12. 什么叫相同语境，为什么如此保守？

按岗位、轮次、难度、真实来源、题干规范空白与 rubric 生成指纹。严格可复算、不会引入第二个模型判断；缺点是语义等价但措辞不同可能漏冲突。现在优先避免误判，不声称理解所有场景等价关系。

### 13. 模型评分本身错了怎么办？

保留原 Evaluation，不把它直接当稳定事实。充分支持却同时存在事实错误说明时标争议；用户可排除该观察或请求后续独立复测。不能说程序已经客观判定模型技术结论一定正确。

### 14. 撤销后为什么不会被重生成报告恢复？

撤销是聚合根上的持久墓碑，重算始终传入；排除集合也始终应用。报告不是能力观察源的新增计数器。V2.2 还切断旧表现层绕回 Main/Blueprint 的路径，否则表面删掉新记忆并不安全。

### 15. 用户直接改成 VERIFIED 更方便，为什么不提供？

“本人声明”不等于“经面试验证”。更正可排除争议、说明原因或撤销推断，但不能制造原始支持证据。本人确认的偏好和经历仍由原提案流程管理，语义不混在一起。

### 16. 同一观察重试或 regenerate 如何避免累计两次？

观察按 Evaluation ID 去重，再从有效记录重算；投影含来源与规则指纹，相同结果不加版本。不是每调用一次 refresh 就加一分。数据库还约束 user/topic 与 memory/revision 唯一。

### 17. 两场同时完成会不会丢一次观察？

能力刷新先获取同 user_id 的事务 advisory lock，再读取观察并重算，锁直到调用者事务结束。另一个完成等前者提交后再计算。没有额外队列；代价是同用户聚合串行，锁顺序和长历史耗时仍需关注。

### 18. 为什么不把模型请求放进同一个数据库事务？

请求可能慢或超时，持锁等待会放大冲突。先持久化 Answer/lease，事务外推理，再短事务核对版本和活动题提交；错误则保存失败状态。必须接受外部调用与数据库不是一个原子事务，再用审计和幂等处理。

### 19. Evaluation 成功，Main 失败，还会扣第二次评分费用吗？

原调用费用已经发生，不能撤销。安全重试可复用同输入/模型/Prompt 的成功审计，避免再次评价；但 Main 重试仍可能产生新费用，且要过剩余预算。不能承诺整个网络过程恰好一次或退款。

### 20. Snapshot 和版本为什么都需要？

ProfileVersion 代表画像版本，但不能单独冻结 JD、Skill、Prompt 和记忆。ContextSnapshot 保存本场实际材料与指纹，后续用冻结值；state_version 管的是会话提交并发，二者职责不同。旧场次不自动升级新规则。

### 21. 记忆怎样影响 Main，又不影响评分？

创建时按相关 Blueprint 最多选3项、限制6000字符；Main 收到验证意图和来源版本，自主决定合法目标。Eval 请求投影移除历史能力推断、approved memory 和风格信息，仍有当前题目、答案及岗位依据。本轮 Live messages 实测验证了这层隔离。

### 22. 你的模型账本能证明服务商没收费吗？

不能。它控制应用用户配额，保存预约与 actual/unknown结算；服务商账单是另一个系统。未知 usage 不计零，实验另外受请求数/Token/时间总上限约束。真实费用未配置价格就不自行估算。

### 23. 为什么现在不引入图数据库、LangGraph 或 Memory 框架？

当前状态、关系和规则用 PostgreSQL 与现有事务能清楚表达，主要问题是来源与一致性，而不是缺框架。引入第二套状态引擎反而增加恢复和预算同步成本。现有数据规模下先保留可靠闭环，未来有复杂执行需求再作选择。

### 24. 你能证明记忆确实提升面试效果吗？

目前只能证明机制和有限行为：Replay 完整验证状态演化，Live 中已验证 Kafka 后选 Redis、冲突后选 Kafka 诊断，且真实 Prompt 带计划。但没有做去记忆对照实验、长期用户评估或全多场 Live，不能报准确率提升。下一步应该先补完整多轮验收和评分质量核对，而不是继续加 Agent。

## 六、最值得现场打开的三处

1. `adaptive.decision_candidates → resolve_selection → validate_decision`：讲真实题源错误与契约修复。
2. `capability_rules.project` 与 `CapabilityMemoryService.refresh/correct`：讲独立验证、冲突、时效与用户控制。
3. `core_service.adaptive_answer → controller.commit_answer/complete`：讲事务外模型、原子提交、审计复用与记忆聚合。
