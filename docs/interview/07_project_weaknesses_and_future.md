# 项目不足、合理演进与不该夸大的内容

## 面试时的总回答

> 这个项目的价值是把模型接入一个有证据、状态和版本边界的完整业务流程，不是已经证明了生产规模。当前主要不足是首次模型调用延迟、材料的结构化覆盖和生成质量。我会优先用固定真实样本验证这些问题，而不是继续增加 Agent 或假装所有场景都已解决。

## 01. 首次 Job Matching 仍有模型延迟

**现状：** 详情读取不再调用模型，一致输入可以复用成功结果；首次新输入仍要等模型。历史拆分测量里 DB 查询约 19.82 ms、模型约 59.612 s；后来一次 Doubao 2.1 匹配为 15915 ms，这不是同输入受控对照。

**影响：** 首次推荐不是普通页面响应速度，用户可能误以为卡住。局部复用不能保证命中率。

**合理演进：** 建立固定 payload 的时延分布与失败类型记录，区分排队、Provider、生成和提交；保留阶段状态和取消/重试语义。在没有测量证明前，不为几秒拆服务。

**不能说：** “已实现稳定秒级推荐”“性能提升了某百分比”。

依据：[分段测量和复用](../37_interview_latency_recovery.md)、[Doubao 匹配记录](../38_product_polish_acceptance.md)。

## 02. LLM 输出质量仍依赖模型

**现状：** Schema、引用验证和 Controller 约束错误的进入方式，但不能证明每道题、每条建议、每次技术评分都最合理。reference answer 是帮助准备的生成内容，不是标准答案认证。

**影响：** 可能出现措辞机械、问题深度不足或不同调用评价波动。有限字面/规则 validator 不是完整语义事实判定器。

**合理演进：** 固定真实项目与答案样本，人工检查相关性、缺失点、追问针对性和参考回答质量；报告可接受与不可接受案例，而不是只保留成功样本。

**不能说：** “完全消除了幻觉”“自动评价等同真人面试官”。

依据：[structured 与业务失败](../31_profile_fact_contract_fix.md)、[当前提问与参考回答](../38_product_polish_acceptance.md)、[主题策略边界](../39_final_topic_ux_acceptance.md)。

## 03. hard eligibility 的结构化覆盖有限

**现状：** 有 SATISFIED / NOT_SATISFIED / UNKNOWN 的确定性判断框架，但真实 Profile 并没有充分可靠的学历、专业、毕业年份资格字段。湖北移动 JD 的博士条件保留，当前真实用户仍 UNKNOWN，不是已满足或已证实不满足。

**影响：** 技术匹配有依据，不代表投递资格已通过。部分地区/专业列表也不是原文完整全集，不能过度过滤。

**合理演进：** 先定义字段、来源与用户确认语义，建立硬资格样本和误判回归，再扩大覆盖。必要的领域变更需另立范围，不能现在偷偷把自由 Memory 或教育描述当硬证明。

**不能说：** “自动准确判断所有招聘资格”“博士不符合场景已经被当前真实数据确定判出”。

依据：[真实岗位与资格限制](../34_real_manual_e2e_readiness.md)、[M6](../24_job_matching_m6.md)。

## 04. Live Search 冻结，真实公共库仍小

**现状：** 第三方 CAPTCHA / rate limit 使真实 SearXNG 不作为前置条件。保留 Gateway、Provider 和 Replay；真实材料通过维护者 MANUAL_SOURCE_IMPORT + LIVE MODEL 入库，不伪造 Fetch。

**影响：** 当前只有有限岗位与审核面经，coverage 不足时无法可靠推荐。人工来源的官方/社区身份不能混淆，转载也不等于独立事实来源。

**合理演进：** 明确资料更新时间、来源身份与审核责任，先维护少量高质量岗位。需要恢复联网时独立验收，不借这次材料整理重新开发搜索。

**不能说：** “实时全网自动补库”“所有导入 JD 都是官方原站”“四岗位五面经覆盖秋招市场”。

依据：[人工来源机制](../33_manual_public_career_import.md)、[九份真实资料状态](../34_real_manual_e2e_readiness.md)。

## 05. 面试真实性改善了，但不等同真人

**现状：** 主题计数、背景上限、连续主题冷却和父题关联改善节奏；最新六轮从项目、RRF 转到 Kafka 与 Query Rewrite，0 个背景问题。去重主要是规范化文本 fingerprint 和已知主题，不是完整语义去重。

**影响：** 复杂同义问题、临场判断和反问的自然程度仍依赖模型。某一场表现好不能代表所有岗位或所有回答。

**合理演进：** 固定短回答、答偏、完整回答和异常路径的案例集，人工评估“是否真的针对上一回答”；逐步维护真实技术主题，而不是机械凑百分比。

**不能说：** “完全复刻企业真实面试”“6/6 技术问题证明所有场次比例稳定”。

依据：[六轮问题与主题限制](../39_final_topic_ux_acceptance.md)。

## 06. Profile 的稳定性与丰富表达有取舍

**现状：** 第一阶段只选证据，summary 可以 null、strengths 为空。代表 statement 是真实 excerpt，但不是多个证据的完整摘要。旧 ResumeReport 仍存在，尚未彻底消除重复语义加工。

**影响：** 某些用户会觉得画像不够“漂亮”；既有下游只读 statement 的规则可能忽略其他引用中的次要技术点。扫描 PDF 和 .doc 也不在当前 Parser 支持范围。

**合理演进：** 在不改变稳定事实的前提下，定义基于 validated facts 的独立显示分析；下游完整消费事实—证据关系需要单独验证，不能靠拼接多个 excerpt 生成新的自然语言断言。

**不能说：** “所有简历格式都能理解”“Profile 已具备无损语义抽取”。

依据：[下游兼容与限制](../32_profile_evidence_selection_contract.md)、[Parser](../../apps/api/src/interview_api/modules/resume/parser.py)。

## 07. 当前是个人本地项目，不是生产规模系统

**现状：** 有安全启动/停止、本地 PostgreSQL 迁移备份、回归和真实模型审计。Provider guard 是进程内；没有生产用户量、QPS、容量、HA、跨实例恢复或在线 SLA 证明。

**影响：** 不能把本地完整 Runtime 说成集群上线。开发环境 JWT、权限、敏感日志、备份恢复和隐私保留策略仍需生产化专项评审。

**合理演进：** 用明确部署目标做安全配置、备份恢复演练、连接/任务容量及跨实例配额验证。先量化现有瓶颈，再决定要不要分布式队列或服务拆分。

**不能说：** “已有生产级高可用”“分布式限流”“Exactly-once 执行”。

依据：[工程交付](../27_engineering_delivery.md)、[当前 guard](../../apps/api/src/interview_api/infrastructure/models/router.py)、[最新边界](../39_final_topic_ux_acceptance.md)。

## 最值得先做的三件事：仅建议，不代表已经实现

1. **硬资格材料覆盖与人工确认**：先减少有实际投递影响的 UNKNOWN，不能用 LLM 猜测补齐。
2. **固定真实样本的质量评估与延迟分布**：使“更像真人”和“更快”有可复核口径，不只是一次体感。
3. **恢复与运行边界复验**：确认断连、鉴权过期、Provider 失败及报告再生成都能正确恢复，再讨论部署规模。

## 面试中被质疑“这还不够成熟”怎么回答

> 是的，我不会把它当生产系统来描述。我证明的是在个人项目范围内，模型怎样受证据、事务和状态控制，真实失败怎样定位与恢复。未验证的规模和质量我会明确留作限制，而不是用 Demo 掩盖。
