# 09 认证与权限设计

## 1. 目标

- 提供基础注册登录；
- 区分普通用户与管理员；
- 保护简历私有数据；
- 保护管理员采集与审核功能；
- 为后续扩展预留空间。

---

# 2. 身份模型

## 2.1 角色

```text
USER
ADMIN
```

## 2.2 权限大纲

### USER

- 使用 QA
- 上传简历
- 查看自己的简历报告
- 查询正式面经库

### ADMIN

- USER 全部权限
- 创建采集任务
- 查看任务详情
- 审核候选内容
- 发布 / 拒绝 / 下架
- 触发重新评分和重新索引

---

# 3. 鉴权方式

采用：

- JWT Access Token

Phase 1 不强制实现 refresh token；  
若后续需要更完整方案，可扩展：

- refresh token
- token rotation
- device session

---

# 4. 密码安全

要求：

- 使用安全哈希算法；
- 不存明文；
- 不在日志打印密码；
- 注册与登录错误不要泄露过多细节。

---

# 5. API 权限依赖

建议：

```python
get_current_user()
require_admin()
```

所有 `/admin/` 接口必须使用 `require_admin()`。

---

# 6. 数据范围控制

## 6.1 简历

普通用户只能：

- 查看自己的 resume；
- 查看自己的 report。

不得通过猜测 ID 获取他人简历。

## 6.2 问答会话

普通用户只能查看自己的 sessions/messages。

## 6.3 正式面经

正式发布内容所有登录用户可查询。

---

# 7. 管理员创建方式

Phase 1 建议：

- 提供脚本 `scripts/seed_admin.py`
- 从环境变量读取管理员邮箱、用户名、密码
- 避免在代码里硬编码默认密码

---

# 8. 前端权限

前端做：

- 登录态判断；
- 管理员菜单显示控制；
- 路由守卫。

但最终权限必须以后端为准。

---

# 9. 审计建议

管理员关键操作记录：

- 创建采集任务
- 发布
- 拒绝
- 下架
- 重新索引
- 重新评分

可写入：

- review_actions
- admin_audit_logs（后续扩展）

---

# 10. 安全边界

1. 管理员后台不得暴露给未登录用户；
2. 文件下载需校验访问权；
3. Object Storage 的原始 key 不直接暴露；
4. 如需下载文件，应走受控 API 或短时签名 URL；
5. 失败信息对普通用户做适度收敛，对管理员后台可显示详细错误。

---

# 11. Phase 1 验收

- 注册可用；
- 登录可用；
- token 生效；
- `/me` 可用；
- admin seed 可用；
- admin API 普通用户无法访问；
- 私有简历数据隔离方案设计清晰。
